# Project Migration Directive

We are NOT performing a traditional code migration.

We are performing a complete software rebuild.

The old project located at:

\Laube-Voyage-app-last

exists ONLY as a visual and business reference.

The new project located at:

\Rebuild-Laube-Voyage-app-last

must be treated as an entirely new software system.

--------------------------------------------------
PRIMARY GOAL
--------------------------------------------------

Preserve ONLY:

• The product idea
• The user experience
• The UI design
• The visual appearance
• The page layouts
• The navigation flow
• The business goals
• The customer journey

Everything else must be reconsidered and rebuilt from scratch.

--------------------------------------------------
THE OLD CODEBASE IS NOT A SOURCE OF TRUTH
--------------------------------------------------

The old implementation contains accumulated technical debt, architectural flaws, duplicated business logic, inconsistent services, security issues, performance bottlenecks, and poor separation of concerns.

Therefore:

DO NOT copy code.

DO NOT copy services.

DO NOT copy APIs.

DO NOT copy helper functions.

DO NOT copy utilities.

DO NOT copy hooks.

DO NOT copy folder structure.

DO NOT copy database queries.

DO NOT copy naming.

DO NOT copy caching logic.

DO NOT copy business implementation.

DO NOT copy authentication flow.

DO NOT copy payment implementation.

DO NOT copy loyalty implementation.

DO NOT copy dashboard implementation.

DO NOT reuse existing architecture.

The old project is a specification of WHAT the application does.

It is NOT a specification of HOW it should be built.

--------------------------------------------------

--------------------------------------------------

• Visual Design

--------------------------------------------------

The new project must follow modern Clean Architecture principles.

Business logic must be separated into independent domains.

Suggested domains include:

Destination Domain

Loyalty Domain

Dashboard Domain

User Domain

Each domain owns:

• Services
• Policies
• Repository layer
• Validation
• Events
• Business rules

No business logic duplication is allowed.

--------------------------------------------------
SINGLE SOURCE OF TRUTH
--------------------------------------------------

Every business rule must exist in exactly one location.

Examples:

Booking lifecycle

Loyalty calculations

Payment validation

Currency conversion

Email sending

Invoice generation

Reward calculations

Discount calculations

Status transitions

must each have exactly one owner.

--------------------------------------------------
THE UI MUST REMAIN IDENTICAL
--------------------------------------------------

The customer should feel that nothing has visually changed.

Pixel-perfect reproduction is required.

Buttons should remain where they are.

Pages should look identical.

The overall experience should feel the same.

Only the internal implementation changes.

--------------------------------------------------
DATA FLOW
--------------------------------------------------

Never attempt to preserve the old execution flow.

Instead:

Understand the business requirement.

Design the optimal architecture.

Implement using modern patterns.

--------------------------------------------------
NO LEGACY LOGIC
--------------------------------------------------

If the old implementation is incorrect,
poorly designed,
duplicated,
or inefficient,

DO NOT recreate it.

Replace it with the best possible engineering solution while preserving the same external behavior.

--------------------------------------------------
ENGINEERING PHILOSOPHY
--------------------------------------------------

Build the system as if Laube Voyage were starting today.

Use everything learned from the previous project.

Avoid every previous architectural mistake.

Optimize for:

• Maintainability
• Scalability
• Performance
• Security
• Reliability
• Observability
• Type safety
• Clear ownership
• Long-term evolution

--------------------------------------------------
FINAL RULE
--------------------------------------------------

Whenever there is a conflict between:

1. Keeping old code

or

2. Building a better architecture

Always choose the better architecture.

Preserve the PRODUCT.

Do not preserve the IMPLEMENTATION.

---

قاعدة فصل العملاء عن موظفي الإدارة والـ Staff:
يجب فصل حسابات موظفي الإدارة عن المسافرين/العملاء في مجموعتين منفصلتين (Two Collections):
- العملاء (Customers): يتم تخزينهم في جدول `customers` ويحتوي سجلهم على نقاط الولاء وعمليات السفر والمفضلات والترقيات والخطافات التلقائية للنقاط، وليس لديهم صلاحية دخول لوحة تحكم الإدارة.
- موظفو الإدارة (Admin / Staff): يتم تخزينهم في جدول `users` ويحتوي سجلهم على صلاحية دخول لوحة تحكم Payload CMS مع دور إداري (`admin` أو `super_admin`) ولا يمتلكون أي نقاط ولاء أو كاش مستويات أو حجز رحلات شخصية لمنع تعقيد الجداول وسد الثغرات الأمنية.

---

قاعدة مراجعة الكود والتدقيق المعماري في بيئة الإنتاج:
إذا كان الهدف من جميع المراجعات المعمارية هو تقييم المشروع بوصفه **نظاماً إنتاجياً (Production Environment)**، فيجب الالتزام بالقواعد التالية أثناء جميع عمليات التدقيق:

* اعتبار المشروع يعمل وفق إعدادات الإنتاج الفعلية فقط.
* عدم إدخال أو مناقشة سيناريوهات **Mock** أو **Unit Tests** أو بيئات الاختبار، ما لم يكن التدقيق موجهاً إليها صراحة.
* عدم اعتبار الفروع الاحتياطية (Fallback Paths) أو الشيفرات المخصصة للتوافق مع بيئات أخرى جزءاً من مسار التنفيذ الإنتاجي، ما لم توجد أدلة تثبت استخدامها في بيئة الإنتاج الحالية.
* عدم إدخال احتمالات مستقبلية أو فرضيات تتعلق بتغيير قاعدة البيانات أو الـ Adapters أو البنية التشغيلية، إلا إذا كانت جزءاً من المشروع الحالي.

وبناءً على ذلك، يجب أن تعتمد جميع الاستنتاجات على **مسار التنفيذ الفعلي في بيئة الإنتاج** كما تحدده إعدادات المشروع الحالية، وليس على وجود فروع احتياطية داخل الكود لم تُستخدم في التشغيل الإنتاجي.

وبعبارة أخرى:

> **يُراجع الكود وفق إعدادات الإنتاج الفعلية للمشروع، وليس وفق الفروع الاحتياطية أو البيئات الاختبارية أو السيناريوهات الافتراضية، ما لم يكن نطاق التدقيق ينص صراحةً على مراجعة تلك البيئات.**

---

قاعدة حظر القيم الافتراضية لقواعد الأعمال (Fail Fast Policy):
يُحظر تماماً استخدام أي قيم افتراضية (Defaults) أو فروع احتياطية (Fallbacks) لقواعد الأعمال (Business Rules) داخل شيفرة التطبيق التنفيذية. أي إعدادات عمل (Business Configuration) مفقودة أو غير صالحة في قاعدة البيانات يجب أن تؤدي فوراً إلى الفشل السريع (Fail Fast) وإطلاق استثناء صريح (`LoyaltyProgramConfigurationException`)، ولا يجوز للكود تعويض البيانات المفقودة بقيم ثابتة مدمجة داخل الكود (Hardcoded Numbers).
تُطبق هذه القاعدة بشكل صارم على جميع النطاقات: الولاء (Loyalty)، التسعير (Pricing)، العملات (Currency)، وسياسات الحجز (Booking Policies).

---

أهم قاعدة حظر مخرجات وتكرار الكود (Strict Non-Duplication Rule):
> **⚠️ لا يجوز أبداً أبداً إنشاء أي ملف أو مجلد أو سطر كود أو دالة جديدة، إلا بعد الفحص الجاد والتدقيق الشامل للتأكد من أنها غير موجودة بالفعل في المشروع، أو موجودة ببيئات/أنماط/مسميات أخرى من صنع الوكلاء السابقين (مثل DTOs أو Loaders أو Widgets أو Helpers أو Projections). يجب إعادة استخدام وتوسيع الملفات والأكواد الحالية المعتمدة دائماً بدلاً من إعادة ابتكارها.**

---

قاعدة حظر إدخال طبقات تجريد مكررة (Universal Abstraction Non-Duplication Rule):
يُحظر تماماً إنشاء أي طبقة تجريد (Abstraction) جديدة أو نمط موازٍ إذا كان المشروع يحتوي بالفعل على طبقة تجريد تؤدي نفس المسؤولية المعمارية داخل النظام.
- إذا كان المشروع يحتوي على `Loader` ──► يُحظر إنشاء `Query` موازٍ.
- إذا كان المشروع يحتوي على `DTO` ──► يُحظر إنشاء `ViewModel` موازٍ.
- إذا كان المشروع يحتوي على `Factory` ──► يُحظر إنشاء `ServiceLocator` موازٍ.
تُطبق هذه القاعدة بشكل كلي ومجرد لمنع التكرار المعماري وضمان الاعتماد على الأنماط القائمة المعتمدة في المشروع بصرف النظر عن المسميات.

---

قاعدة التدقيق المعماري وتفضيل التوسيع على الموازاة (Architectural Audit & Extension Over Parallel Structures Rule):
> **Before introducing any new architectural abstraction (folder, file, service, helper, DTO, loader, query, builder, mapper, registry, hook, provider, utility, or component), an architectural audit must first prove that no equivalent abstraction already exists anywhere in the project. Preference must always be given to extending the existing architecture over introducing parallel structures.**
> 
> (قبل تقديم أي تجريد معماري جديد — سواء كان مجلداً، ملفاً، خدمة، دالة مساعدة، DTO، Loader، Query، Builder، Mapper، Registry، Hook، Provider، Utility، أو Component — يجب أولاً إجراء تدقيق معماري يثبت عدم وجود تجريد مكافئ بالفعل في أي مكان بالمشروع. يجب دائماً إعطاء الأولوية القصوى لتوسيع البنية المعمارية القائمة بدلاً من إدخال هياكل موازية).
