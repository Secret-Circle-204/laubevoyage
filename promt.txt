# Project Migration Directive

We are NOT performing a traditional code migration.

We are performing a complete software rebuild.

The old project located at:

\Laube-Voyage-app-last

exists ONLY as a visual and business reference.

The new project located at:

\Rebuild-Laube-Voyage-app-last

must be treated as an entirely new software system.

--------------------------------------------------
PRIMARY GOAL
--------------------------------------------------

Preserve ONLY:

• The product idea
• The user experience
• The UI design
• The visual appearance
• The page layouts
• The navigation flow
• The business goals
• The customer journey

Everything else must be reconsidered and rebuilt from scratch.

--------------------------------------------------
THE OLD CODEBASE IS NOT A SOURCE OF TRUTH
--------------------------------------------------

The old implementation contains accumulated technical debt, architectural flaws, duplicated business logic, inconsistent services, security issues, performance bottlenecks, and poor separation of concerns.

Therefore:

DO NOT copy code.

DO NOT copy services.

DO NOT copy APIs.

DO NOT copy helper functions.

DO NOT copy utilities.

DO NOT copy hooks.

DO NOT copy folder structure.

DO NOT copy database queries.

DO NOT copy naming.

DO NOT copy caching logic.

DO NOT copy business implementation.

DO NOT copy authentication flow.

DO NOT copy payment implementation.

DO NOT copy loyalty implementation.

DO NOT copy dashboard implementation.

DO NOT reuse existing architecture.

The old project is a specification of WHAT the application does.

It is NOT a specification of HOW it should be built.

--------------------------------------------------
WHAT MAY BE REUSED
--------------------------------------------------

The old project may only be used as a reference for the following:

• Visual Design
• Layouts
• Formatting
• Colors
• Typography
• Icons
• Animation
• Component Appearance
• Responsiveness
• User Interaction
• Navigation
• Page Structure (excluding Destination Logic). Destination will contain countries, each country will contain cities, and each city will contain a Tour Package or Daily Tour.

• Functional Requirements
• Workflow



However, all data retrieval, state management, services, caching, and rendering logic must be newly designed.

--------------------------------------------------
ARCHITECTURE PRINCIPLES
--------------------------------------------------

The new project must follow modern Clean Architecture principles.

Business logic must be separated into independent domains.

Suggested domains include:

Destination Domain

Package Domain

Booking Domain

Payment Domain

Loyalty Domain

Dashboard Domain

User Domain

Review Domain

Notification Domain

Localization Domain

Currency Domain

Media Domain

Admin Domain

Each domain owns:

• Services
• Policies
• Repository layer
• Validation
• Events
• Business rules

No business logic duplication is allowed.

--------------------------------------------------
SINGLE SOURCE OF TRUTH
--------------------------------------------------

Every business rule must exist in exactly one location.

Examples:

Booking lifecycle

Loyalty calculations

Payment validation

Currency conversion

Email sending

Invoice generation

Reward calculations

Discount calculations

Status transitions

must each have exactly one owner.

--------------------------------------------------
THE UI MUST REMAIN IDENTICAL
--------------------------------------------------

The customer should feel that nothing has visually changed.

Pixel-perfect reproduction is required.

Buttons should remain where they are.

Pages should look identical.

The overall experience should feel the same.

Only the internal implementation changes.

--------------------------------------------------
DATA FLOW
--------------------------------------------------

Never attempt to preserve the old execution flow.

Instead:

Understand the business requirement.

Design the optimal architecture.

Implement using modern patterns.

--------------------------------------------------
NO LEGACY LOGIC
--------------------------------------------------

If the old implementation is incorrect,
poorly designed,
duplicated,
or inefficient,

DO NOT recreate it.

Replace it with the best possible engineering solution while preserving the same external behavior.

--------------------------------------------------
ENGINEERING PHILOSOPHY
--------------------------------------------------

Build the system as if Laube Voyage were starting today.

Use everything learned from the previous project.

Avoid every previous architectural mistake.

Optimize for:

• Maintainability
• Scalability
• Performance
• Security
• Reliability
• Observability
• Type safety
• Clear ownership
• Long-term evolution

--------------------------------------------------
FINAL RULE
--------------------------------------------------

Whenever there is a conflict between:

1. Keeping old code

or

2. Building a better architecture

Always choose the better architecture.

Preserve the PRODUCT.

Do not preserve the IMPLEMENTATION.
